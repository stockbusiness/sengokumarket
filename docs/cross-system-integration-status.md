## 2. 千ノ国ウォレット連携の要点(新規入手分)

### 2.1 認証方式が代理店システムと異なる

代理店システムは単純な`x-api-key`/`Authorization: Bearer`でしたが、ウォレットは**HMAC-SHA256署名認証**です。

```
X-OVE-Api-Key: ovk_...
X-OVE-Timestamp: <UNIXエポックミリ秒>
X-OVE-Nonce: <リクエストごとに変わるランダム文字列>
X-OVE-Signature: HMAC-SHA256(signing_secret, "<timestamp>.<nonce>.<method>:<path>:<raw body>")
```

署名対象文字列のJSON文字列化(キー順序・エスケープ)を送受信で完全一致させる必要があり、代理店システム連携より実装難易度が高い。タイムスタンプ許容ずれ±5分、nonceは使い捨て(リプレイ拒否)。

### 2.2 冪等性キーの扱いが代理店システムと異なる

代理店システム: `Idempotency-Key`HTTPヘッダー。
ウォレット: **リクエストボディのフィールド**`idempotency_key`。同じキーで再送すると新規取引を作らず既存取引をそのまま返す(エラーにならない)。

### 2.3 主要エンドポイント

| メソッド/パス | 用途 | 想定する利用場面 |
|---|---|---|
| `POST /api/v1/rewards/grant` | ポイント付与 | 決済確定時の購入特典ポイント付与(方針書§19.4) |
| `POST /api/v1/transactions/debit` | ポイント利用(減算) | チェックアウトでポイント消費を許可する場合 |
| `POST /api/v1/transactions/{id}/reverse` | 取消 | 全額返金時の特典取消(方針書§22) |
| `GET /api/v1/service/accounts/{externalUserId}/balance` | 残高照会 | 自サービスに紐づく利用者の残高表示 |

`amount`等はBigInt文字列で返るため、数値としてではなく文字列として扱う実装が必要。

### 2.4 未確認事項(このシステムに関するもの)

1. **`service_code`の確定**: `ServiceCode`一覧に`SENGOKU_EC`があり、戦国楽市楽座を指す可能性が高いが未確認(`NFT_MARKET`という候補も存在する)
2. **既存クーポン機能のマッピング方法**: このガイドのAPIは「ポイント(OVE表示残高)」という単一の台帳を前提にした汎用APIで、クーポン固有のルール(対象商品限定・最低購入額・%/定額割引の計算・併用可否)を扱う専用エンドポイントが見当たらない。既存のクーポン機能をこの台帳にどうマッピングするか(そもそもマッピングする設計なのか)は未確定
3. **APIキー・署名鍵の発行手続き**: 現状セルフサービス機能はなく、運用担当者への手動依頼が必要。まだ依頼していない
4. **`transaction_type`と`reward_rules`の事前登録**: 購入特典ポイント付与用の`transaction_type`が運用担当者側で設定済みか未確認

## 3. 戦国パスポート連携の要点

戦国パスポートのガイドは「パスポート⇔代理店システム」の連携仕様であり、「このショッピングシステムからパスポートへ購入後の権利付与を依頼するAPI」は元々存在しなかった。問い合わせた結果、以下が判明した。

- パスポート側も「参加国・役割・利用権」の自動付与の仕組みは未実装で、`/admin/external-orders`からの**手動5ステップ操作**(登録→入金確認→ユーザー紐付け→区画割当→権利付与)で運用されている(`docs/external-purchase-operation-manual.md`)。このシステムで実装した「外部購入者の取り込み」機能と同じ発想の仕組みが、パスポート側にも既に存在する
- 「参加国・役割・利用権」は実装上バラバラの別概念だった: 利用権=土地区画(城主プラン)所有権、役割=城主ロール、参加国=購入と無関係(ガチャで獲得、`is_nation_builder`は手動編集のみ)
- パスポート側は、具体的に何を付与したいか明確になれば、`/api/integrations/agencies`と同型のイベント型API(`event: "purchase.confirmed"`/`"purchase.refunded"`)を新設する用意がある、との回答だった

**【決定事項・2026-07-14】** 戦国楽市楽座の評議員デジタル会員証NFTは、当面パスポート側のいずれの概念(土地区画所有権・城主ロール・`is_nation_builder`等)にも対応させず、**パスポートとの連携自体を行わない**方針で確定。そのため上記イベント型APIの設計は現時点では不要。

なお、参考になった設計パターンとして記録しておく:

- 未対応イベント(`lead_created`/`common_user.merged`等)を200で受理し処理をスキップする設計は、このシステムの実装と同じ考え方
- 共通顧客ID解決・紹介capture/confirmの送信を「タイムアウト5秒・失敗は握りつぶし・呼び出し元の主処理をブロックしない」というベストエフォート方式にしている点は、このシステムで検討中の方針(千ノ国5システム方針書の項目8)と一致し、実装時の参考にできる
- エラー形式はパスポート側もまだ旧形式のままで、新形式への統一は未対応(このシステムの方が対応が進んでいる)
- `common_user_id`はログイン確定時の遅延解決方式で、既存ユーザーへの遡及発行バッチはパスポート側にも存在しない。将来共通ID連携を行う場合、遡及発行が必要ならこちら側で自前のバッチを用意する必要がある
- `referral_token`の発行元不一致(パスポート自前の`?ref=`リンクのagent_codeと、sengoku-ai.com側が想定するLP発行のreferral_tokenが食い違う可能性)は、パスポート側からsengoku-ai.comへ問い合わせ済みだが回答待ち。このシステムで将来紹介トラッキング連携を検討する際は同じ懸念が該当し得るため留意する
