# 代理店ポータル SSO連携 仕様書(ドラフト)

**ステータス: ドラフト。代理店システム側チームとの協議・合意前提。合意後に正式版として`docs/`配下に確定する。**

戦国楽市楽座(以下「本システム」)の代理店ポータル(`/agency`)へ、代理店システム(以下「IdP」)に既にログイン済みの代理店担当者が、パスワード再入力なしでワンクリック遷移できるようにするための連携仕様。

対象読者: 代理店システム側の開発者。

## 1. 背景・目的

- 現状、代理店担当者は本システムの代理店ポータルへメールアドレス・パスワードで個別にログインする必要がある。
- 代理店担当者は日常的にIdP(代理店システム)に先にログインしているため、そこから「本システムの代理店ポータルを開く」ボタン一つで、パスワード入力なしに遷移できるようにしたい。
- **今後、代理店システムから連携するサービスが本システム以外にも増える想定のため、本仕様は特定のサービス向けではなく、IdPが発行する共通のSSOトークンを各サービス(Relying Party、以下「RP」)がそれぞれ検証する、という汎用的な構造にする。** IdPは発行の仕組みを一つ実装すればよく、RPが増えるたびにIdP側の実装を増やす必要はない。

## 2. 全体の流れ

1. 代理店担当者がIdPにログインした状態で、「本システムの代理店ポータルを開く」ボタンを押す。
2. IdPが、その代理店(`external_id`)向けの短期間有効なSSOトークン(署名付きJWT)を発行する。
3. IdPが代理店担当者のブラウザを `https://<本システムの本番ドメイン>/agency/sso?token=<JWT>` へリダイレクトする。
4. 本システムがトークンを検証し、対応する代理店ポータルアカウントで通常ログインと同じセッションCookieを発行、`/agency`へリダイレクトする。
5. トークンが無効・期限切れ・既使用の場合は、本システムの通常ログイン画面(`/login`)へエラーメッセージ付きで戻す(パスワードログインへのフォールバック)。

このシステムに購入者としての紐づけを持たないアカウント発行前の代理店(まだ`login_email`未連携)については、本システムは「代理店ポータル未連携です」という案内を表示する(6章参照)。

## 3. トークンの署名方式

- **IdPの秘密鍵で署名し、RPは公開鍵のみで検証する非対称署名(JWT / RS256)を採用する。** 階層同期API(`docs/api-agency-integration.md`)で使っている固定APIキー方式(共有秘密鍵)は今回は使わない。RPが増えるたびに個別の共有秘密鍵をIdP側で管理・配布する必要が生じ、漏えい時の影響範囲もRPごとに個別管理が必要になるため。
- IdPは公開鍵を次のいずれかの方法でRPに提供する。
  - (推奨) JWKS形式で `https://<IdPのドメイン>/.well-known/jwks.json` を公開し、RPが起動時・定期的に取得してキャッシュする。鍵ローテーションが必要になった場合もRP側の再設定なしに追従できる。
  - 簡易運用でよい場合は、公開鍵(PEM形式)を本システムの管理画面(`/admin/settings`)に直接登録してもらう形でも可(この場合、鍵ローテーション時はIdP・RP双方で手動更新が必要)。
- どちらの方式を採るかは協議事項とする。

## 4. トークンのクレーム(ペイロード)

| クレーム | 型 | 必須 | 説明 |
|---|---|---|---|
| `sub` | string | ○ | 対象代理店の`external_id`(既存の階層同期APIと同じ値) |
| `aud` | string | ○ | 遷移先RPの識別子。本システム向けは `"sengoku-rr"` を割り当てる想定(他RPが増えたら別の値を発行) |
| `iat` | number | ○ | 発行時刻(UNIX秒) |
| `exp` | number | ○ | 有効期限(UNIX秒)。**発行から60秒以内を推奨。** ブラウザリダイレクト1回で使い切る前提のため、長い有効期限は不要かつリスク |
| `jti` | string | ○ | トークンの一意ID(UUID等)。RP側でのリプレイ防止(一度使用したjtiの再利用を拒否)に使用 |
| `contact_email` | string | - | 参考情報。RP側での本人確認補助用(必須の突合キーではない) |

**リクエスト例(IdPが発行するJWTのペイロード、署名前)**

```json
{
  "sub": "agency-001",
  "aud": "sengoku-rr",
  "iat": 1735600000,
  "exp": 1735600060,
  "jti": "e3b0c442-98fc-4c9e-8f8a-1f2d3c4b5a6f"
}
```

## 5. 本システム側のエンドポイント

```
GET /agency/sso?token=<JWT>
```

- 公開鍵(またはJWKS)でJWT署名を検証する。
- `aud`が`"sengoku-rr"`であることを確認する。
- `exp`超過・`jti`の再利用(既に一度使用済み)を検知した場合は拒否する。`jti`は本システム側で短期間(有効期限+αの間だけ)記録し、使用済みかどうかをチェックする。
- 検証成功後、`sub`(`external_id`)から対応する`Agency`を特定し、そのAgencyに紐づく代理店ポータルアカウント(`User.role = 'agency'`)を検索する。
  - 見つかった場合: 通常ログイン(`POST /auth/login`)と同じ方法でJWTセッションを発行し、httpOnly Cookieをセットして`/agency`へリダイレクトする。
  - 見つからない場合(まだ`login_email`連携が済んでいない代理店): `/login`へ`error=agency_not_linked`等のクエリ付きでリダイレクトし、「代理店ポータルのご利用には事前連携が必要です」という案内を表示する。
- 検証失敗(署名不正・期限切れ・aud不一致・jti再利用)の場合: `/login`へ`error=sso_failed`等のクエリ付きでリダイレクトし、通常のメールアドレス・パスワードログインへフォールバックさせる。

この一連の処理はブラウザのリダイレクトで完結するAPIエンドポイントであり、`{error:{code,message}}`形式のJSON APIではない(ユーザーの画面遷移が主目的のため)。

## 6. 代理店ポータル未連携の代理店について

- 本仕様は、既存の階層同期API(`docs/api-agency-integration.md` 6章)で`login_email`を指定してポータルアカウントが発行済みの代理店にのみ適用される。
- SSOトークンの`sub`(`external_id`)に対応する代理店ポータルアカウントがまだ存在しない場合、IdP側では「本システムの代理店ポータルを開く」ボタン自体を非表示にする(または押せないようにする)ことを推奨する。本システム側でも保険として5章のフォールバックを用意する。

## 7. 今後の拡張(他RP追加時)

- 新しいRPを追加する場合、IdPは`aud`に新しい識別子を割り当てて同じ発行ロジックを再利用するだけでよい(発行エンドポイント自体の実装変更は不要な設計とする)。
- 各RPは、公開鍵(またはJWKS)の取得方法と検証ロジックさえ実装すればよく、IdPとの間で個別の秘密鍵をやり取りする必要はない。

## 8. 未確定事項(協議が必要な点)

- 公開鍵の提供方式(JWKS公開 vs. 管理画面への手動登録)。
- `aud`の識別子命名規則(サービスごとにどう払い出すか)。
- IdP側の「本システムの代理店ポータルを開く」ボタンの設置場所・トークン発行APIのエンドポイント仕様(こちらはIdP側の実装詳細のため、先方から仕様を提示してもらう形でも可)。
